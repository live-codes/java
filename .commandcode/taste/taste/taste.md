# Taste
- Windows dev machine: POSIX utilities (`head`, `tail`, `mv`) are unavailable in the default shell — use PowerShell (`Invoke-WebRequest`, `Move-Item`, `Get-Content`) or cmd builtins (`del`, `dir`) for shell/file operations. Confidence: 0.9
- Global npm config sets `omit=dev` (devDependencies skipped by default) — install with a one-off `npm install --include=dev`; don't modify the user's global config. Confidence: 0.9
- `agent-browser` skill (headless Chromium/CDP) is the preferred tool for verifying browser PoCs/builds end to end: open page, poll status, read results from localStorage JSON, screenshot evidence, then close. When its native binary is missing/broken (as on this Windows box), fall back to launching an installed Chrome/Chromium with `--headless=new --remote-debugging-port` and driving it over CDP with a small Node script (Node 24 has a global `WebSocket`) instead of giving up on browser verification. Confidence: 0.85
- PoC-first, benchmark-gated decisions: standalone HTML PoCs measuring cold start / compile / run / download size + a feature matrix, results recorded in `poc/RESULTS.md` (with screenshots), and the engine/dependency choice made only after applying the gate. Confidence: 0.7
- Prefer mirroring proven reference implementations (upstream playground code, sibling integration repos like fsharp-wasm/vb-wasm) and existing in-repo conventions over inventing new patterns: when adding a new engine, wants it to slot into the established house pattern "like other languages" (e.g. LiveCodes' `X`/`X-wasm` language pairing with the plain name as the default and `-wasm` the wasm engine). Confidence: 0.8
- Wants a simple, standalone HTML playground for each language/engine — write code → run in the browser, no framework or build step — and asks for new ones to match the look and structure of the existing playgrounds (e.g. the Rust `index.html`) rather than getting a fresh design. Confidence: 0.75
- Prefers phased delivery: scope Phase 1 to the smallest end-to-end slice that demonstrably works (e.g. Java + stdin), and explicitly defer the harder/larger work (Kotlin/Scala, dependency version bumps) to a later phase rather than attempting everything at once. Confidence: 0.7
- When swapping an engine behind an existing API, keep the public API surface identical — existing embeds/templates/consumers must keep working unchanged. Confidence: 0.6
- Vendor/pin third-party runtime artifacts (checksums, pinned URLs) and document provenance + licenses in the README rather than hot-linking one-off CDNs — protects against bus-factor of small upstream forks. Confidence: 0.6
- Open-source engines only: reject proprietary runtimes whose licenses require payment for commercial/self-host use (CheerpJ was ruled out for LiveCodes); MIT/Apache preferred. Confidence: 0.6
- When the ideal path requires a heavy local toolchain (JDK, Binaryen, etc.), prefers shipping the capability now from pinned prebuilt artifacts and deferring the from-source build to CI, rather than blocking progress on a long local install/build. Confidence: 0.6
- User gives terse go-aheads ("continue", "yes, do that and apply all fixes", "yes, continue fixing") — treat them as "proceed with your recommended defaults / carry out your own recommendations", state the locked-in decisions, and keep moving instead of re-asking decision questions. Confidence: 0.75
- Approves comprehensive fixes rather than minimal ones: when a set of defects has been identified, wants all of them applied ("apply all fixes") and the outcome optimized end-to-end ("reduce regression as much as possible"), not just a single targeted patch. Confidence: 0.55
- Do not `git init`, commit, or push unless explicitly asked; if work is uncommitted, note that fact in the wrap-up instead of committing proactively. Confidence: 0.55
- Clean up after verification runs: kill background shell tasks, stop headless browsers, and free listening ports once the work is done. Confidence: 0.5
- In exploration/spike tasks, explicitly welcomes answers that abandon the current architecture ("options that do not use the current setup and use a totally different way are still acceptable") — survey the full space and don't anchor the search to the existing engine or stack. Confidence: 0.7
- Judges package boundaries by whether components share actual tooling/steps (artifacts, worker/runtime model, browser feature gates, licence, upstream) rather than by API similarity — prefers a separate package per language toolchain (matching rust-wasm, fsharp-wasm, …) and pushes back when a proposed fallback would re-couple two packages. Confidence: 0.6
- Does not accept a working-but-unusable core path as "documented limitation": when a path is effectively broken (e.g. a compile that never finishes), wants the root cause investigated and fixed — and if it stays unusable even after the bugs are fixed, cut it entirely rather than shipping it as an experimental/limited option (e.g. dropped Kotlin and scoped the package to Java only). Confidence: 0.65
- Wants behavioural/compatibility claims verified by measurement against the real artifact rather than documentation or memory: e.g. which Java version a running program actually reports, and an actual cross-browser matrix (Chrome/Edge/Firefox — with Safari explicitly flagged as unverified when it can't be tested here) rather than documented support. Confidence: 0.65
- When a downstream workaround is functioning, still redirects effort to fixing the actual root cause in the upstream/source code rather than shipping the workaround ("no need to work on the file bridge ... fix the StdlibConverter bug"); treat the local patch as temporary. Confidence: 0.7
- Rejects or de-prioritizes work that has marginal value for the target environment (e.g. told to skip the browser file-I/O bridge) — focus on the fix that matters for the real use case. Confidence: 0.55
- When deciding whether to adopt or switch a dependency/engine, wants a full *honest* side-by-side comparison — grounded in measured numbers, but explicitly listing the disadvantages, risks, and unknowns (browser coverage, library-subset gaps, unmaintained upstream) rather than a one-sided pitch, so the decision rests on data. Confidence: 0.6
- Wants visibility into long-running steps: proactively report progress/ETA and flag upfront when an operation will take many minutes, rather than leaving long silent gaps (pushing back on an ~80-minute step with "Is that expected? What is the progress?"). Confidence: 0.55
- When replacing an existing engine/dependency with a faster or newer one, approves gating the switch on *functional-parity* evidence, not just performance numbers: run the same representative corpus of real programs through both engines, diff the outputs, and treat any "works today, breaks on the new one" regression as the deciding factor (accepting a switch only at zero regressions, or with an explicit documented subset). Confidence: 0.55
